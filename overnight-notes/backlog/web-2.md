## WEB2-01 The people sheet is a 400 KB SVG rasterised on the main thread at startup; a 7.9 KB PNG is pixel-identical

- **Measured.** `public/sprites/people/people.svg` is 399,710 B, 128x1920, made of 6,640 `<rect>` elements in 44 colours (gzip 31,293 B, brotli 15,693 B). Headless Chrome, first load + decode + rasterise into a canvas: **122.0 ms** (later loads of the same SVG, cache-busted, median 21.4 ms). The same sheet as a PNG: **1.8 ms** first, 1.2 ms median. Chrome's own rasterisation of the SVG, written back out as PNG and then optimised with ImageMagick, is 7,888 B and decodes to the same RGBA (`magick ... rgba` identical). Lossless WebP of the same pixels: 4,316 B.
  - Pixel check: an ImageMagick-rendered PNG was *not* identical (transparent pixels became opaque), so the PNG must come from Chrome's rasteriser, not from magick. Re-verified with Chrome output.
- **Where.** `src/shared/sprites.ts:34` (`ATLAS_PEOPLE = loadAtlas('.../people.svg')`, module init, so it starts on the GPU path as soon as `WorldView` evaluates via `cf/atlas-hooks.ts:53` and `shared/sprites.ts:45-53`). Rasterised by `src/shared/rasterized-atlas.ts:3-22`. Tests that read the SVG: `src/game/render/character-visuals.test.ts:160`, `src/shared/rasterized-atlas.test.ts:15`, `src/shared/sprites.test.ts:55`.
- **Change.** Commit a PNG (`people.png`, 7.9 KB, generated by drawing the current SVG into a canvas in Chrome and optimising), point `sprites.ts:34` at it, and keep the SVG in the repo as the source with a short script that regenerates the PNG. Update the three tests that read the SVG or the rasterised canvas. Keep the `rasterizedAtlas` path (it still copies to canvas). Add a test that the PNG's pixels match the SVG rasterised in the test environment where that is possible, or a golden hash in the regenerate script.
- **Expected gain.** About **-120 ms** of main-thread time on the first map load on this Mac (scaled by CPU, maybe 0.5 s on a 4-6x-throttled machine, unmeasured). Transfer **-23.4 KB gzip / -7.8 KB brotli**. Each reload after a cache hit saves about 20 ms.
- **Risk.** Low. Pixel equality is verifiable. Watch the sheet's sRGB handling: use the same canvas path for both sides. The three tests are the only callers that would need updates.

## WEB2-02 Two eager 1-2 MB PNG sprite sheets: lossless WebP saves 0.48 MB, q90 WebP saves 1.47 MB

- **Measured.** `vegetation-v2.png` 1,224,446 B (1774x887 RGBA, 334,062 unique colours, so no palette win) and `fauna-v2.png` 878,525 B (184,037 colours). Both are PNG, so the wire bytes equal the file size (gzip gains nothing). Both are needed on the GPU path: `trees-driver.ts:97` gates on `vegetationAtlasReady()` from `vegetation-sprites.ts`, and `AnimalSpriteLayers.tsx:24` uses `useFaunaAtlas()`.
  - Lossless WebP (`cwebp -lossless -z 9`): 970,340 B and 653,764 B, **-478,867 B total (-22.8 %)**.
  - Lossy WebP q90 (`-q 90 -alpha_q 100`): 383,354 B and 250,990 B, **-1,468,627 B (-69.8 %)**. Needs a visual diff on pixel art, not done.
  - Decode and draw in Chrome (`drawImage` into a canvas, median): lossless WebP 16.5 ms (vegetation) / 16.7 ms (fauna) vs PNG 12.9 / 11.3 ms. So WebP costs about **+4-5 ms once per sheet** at bake time. Lossy WebP was 20.7 / 16.7 ms.
- **Where.** `src/game/render/vegetation-sprites.ts:3`, `src/game/render/fauna-sprites.ts:4`, `src/game/render/cf/atlas-hooks.ts:66-70` (`FAUNA_URL`, `useFaunaAtlas`), `public/sprites/*.png`.
- **Change.** Ship `vegetation-v2.webp` and `fauna-v2.webp` (lossless first). Only the URL strings change, plus a fallback to the PNG if the image fails to load (all browsers the app targets support WebP). Lossy q90 only after a side-by-side check of the crops in `vegetation-sprites.ts:4-16` and the fauna cells.
- **Expected gain.** Eager transfer 3,603,322 -> 3,101,050 B (**-13.9 %**) with lossless only, -> 2,111,290 B (**-41.4 %**) with lossy q90 (both include WEB2-01). Decoded size is unchanged (1774x887x4 = 6.29 MB each), so no memory gain.
- **Risk.** Lossless: none for the pixels (verify byte-equal decode). Lossy: visible colour/edge change on pixel art; needs review.

## WEB2-03 Organism cards re-render about 160 times a second while the right panel is open

- **Computed.** `RightPanel` renders up to `LIVE_PAGE_SIZE = 80` `OrgCard`s (`ui/panels/RightPanel.tsx:31`, `:57-`). The world is published to React every 500 ms (`simulation/useSimulation.ts:117` `REACT_THROTTLE_MS = 500`). `OrgCard` is `memo`, but it subscribes through `useOrganism(orgId)` = `useWorldStore(s => s.byId.get(id))` (`state/worldStore.ts:46-48`) and `ui/panels/OrgCard.tsx:42`. The merge reuses an organism's record only when **no** field changed (`simulation/merge.ts:4-22`). Living people move and age every tick, so the record identity changes and every visible card re-renders at each publish: **80 cards x 2/s = 160 `OrgCardImpl` renders/s** while the panel is open.
- **Measured?** No. The per-render cost is not measured. The panel is closed by default (`state/ui/slices/panels.ts:14` `panelOpen: false`), and the backlog's React numbers (20-27 ms per 10 s, `web.md`) were taken with it closed, so this path is not in the existing measurements.
- **Change.** Give the card a view-model selector that returns only the fields the card draws (name, age, generation, traits rounded to the displayed precision, memory counts, status, starred), with `useShallow` or a custom equality, so the card re-renders only when displayed text changes. Alternatively pass a stable snapshot per card from `RightPanel`. Then add a bench scenario with the panel open (also covers WEB-25's missing scenario) to measure renders/s and ms/s before and after.
- **Expected gain.** Up to 160 renders/s removed when the displayed values are unchanged, which is most ticks for most cards (the card shows rounded fields). Unmeasured; order of 1-3 % of one desktop core while the panel is open, several times that on a throttled machine (estimate).
- **Risk.** Low-medium: the card has inline editing (`renamingOrgId`) and tooltips; the selector must include every field the JSX reads. A lint-level check: list the `org.` reads in the file.

## WEB2-04 Verify that the production host compresses the 3.8 MB wasm (conditional gain 2.7 MB)

- **Measured.** `sim_core_bg-*.wasm` is 3,818,232 B. gzip-9 1,086,111 B, brotli-11 781,572 B. `public/_headers` sets cache headers for `/assets/*` (immutable) but sets **no** `Content-Encoding` and says nothing about compression. The local server here (python `http.server`) does not compress, so the production number is unknown from this machine.
- **Where.** `public/_headers:1-30`; `src/simulation/wasmWorker.ts:432` (the fetch is inside `init`).
- **Change.** No code change until verified. If it is not brotli or gzip, configure the host (Cloudflare Pages compresses by default, so this is most likely a non-issue) or pre-compress the asset at build time.
- **Expected gain.** If uncompressed: **-2.7 MB** on the first visit (3.8 MB raw vs 1.09 MB gzip). If compressed: nothing.
- **Risk.** None for the check. Pre-compressing would need care with the `Content-Encoding` header and the preload hint (`index.html:50`).

## WEB2-05 Two 4-5 MB people canvases are held for the whole session

- **Computed from constants.** The people look atlas is `HUMAN_ATLAS_WIDTH x HEIGHT` = 128 x 7680 (4 frames x 32 px; 5 stages x 2 sexes x 24 appearances x 32 px) = **3,932,160 B** RGBA. The sheet raster is 128 x 1920 = **983,040 B**. `usePeopleAtlas` (`cf/atlas-hooks.ts:52-64`) copies the look atlas into a second canvas of the same size with `useDynamicCanvas` (3,932,160 B). The intermediate is kept alive for the session: `lookAtlases` (`shared/sprites.ts:57`) is a `WeakMap` keyed by the sheet canvas, and that canvas is kept by `rasters` (`shared/rasterized-atlas.ts:1`) keyed by the module-level `ATLAS_PEOPLE` image. Build-time transients: `getImageData` 983 KB + `createImageData` 3.93 MB in `buildPeopleLookAtlas` (`cf/people/people-looks.ts:141-153`).
- **Where.** `src/shared/sprites.ts:42-57`, `src/shared/rasterized-atlas.ts:1-22`, `src/game/render/cf/atlas-hooks.ts:52-64`. The canvas fallback (`game/render/layers/people.ts:56`) and `cf/scenes/CfRoomView.tsx:209` also call `getPeopleAtlas()`, so the look atlas is needed there.
- **Change.** On the GPU path, build the look atlas straight into the dynamic canvas (or drop the intermediate after the copy), and release the sheet canvas once the looks exist. Keep the cache for the fallback and the room view, rebuilding on demand.
- **Expected gain.** About **-3.9 MB** resident for the session (the look atlas), and up to **-0.98 MB** more for the sheet canvas. Also avoids a one-time 4.9 MB transient at startup. Heap/GPU, no CPU change.
- **Risk.** Low-medium: the fallback and room view share `getPeopleAtlas`. Keep the same pixels (the build code is unchanged).
- **Related, not counted.** The decoded sprite images retained by `loadAtlas` (`shared/sprites.ts:17-27`) are 6.29 MB decoded each for vegetation and fauna (1774x887x4). Whether Chrome keeps the decoded frames for an unused `Image` was not measured; `drawVegetationSprite` still reads its `Image` every frame, so it cannot simply be dropped.

## WEB2-07 The people and fauna sheets start loading only after `WorldView` evaluates (no preload)

- **Computed from code.** The image requests start at module evaluation: `shared/sprites.ts:32-34`, `game/render/vegetation-sprites.ts:3`, and at mount for fauna (`cf/atlas-hooks.ts:69-70`). `WorldView` itself is only modulepreloaded (`index.html:52`), so the sheets wait for the 387 KB chunk to download and evaluate. `index.html:49-52` preloads only the wasm and the two chunks.
- **Measured?** Not in the browser. In a headless cold load the app stayed on the splash for 25 s of virtual time, and the sprite requests never appeared in the server log (only the chunks and the wasm did). So the wait is computed from code, not timed.
- **Change.** Add `<link rel="preload" as="image" href="/sprites/people/people.svg" fetchpriority="low">` (or the PNG after WEB2-01) and the same for `vegetation-v2` and `fauna-v2` to `index.html`, after the wasm preload. `fetchpriority="low"` keeps them behind the 3.8 MB wasm. Alternatively import the URLs in the entry so they are discovered with the chunk graph.
- **Expected gain.** Unknown: at most the time between the first `WorldView` evaluation and the sheet arrival, which is the time to first trees and animals (not the first frame). Needs a trace (Chrome Performance panel on the throttled profile) before it is worth a PR.
- **Risk.** Low. Extra preloads compete with the wasm for bandwidth, hence `fetchpriority="low"`. Measure with and without.
